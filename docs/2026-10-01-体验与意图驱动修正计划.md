## 要求与建议的分界

哥哥明确要求：体验以 SOTA 为目标；不做审核；一切收录和过滤以使用者意图为准；允许约定，不允许审查。此前明确要求两种安装方式、安装详情、gh 缺失时禁用与提示、官方全部安装来源、操作审批。

以下界面组织、优先级、缓存策略和验收数值是织提出的方案，不是已有的个人要求。SOTA 在此作为目标，不宣称已达到行业最优。

## 行为边界

- 默认 GitHub 查询仍使用 topic:dsh-plugin，这是哥哥已选定的发现约定。它不证明插件已被官方认可，也不是订阅或手动安装的准入条件。
- 可以自选来源、自定义查询、增删订阅、指定包含或排除条件、隐藏某一条、选择排序。选择可见、可撤销、可保存；重置恢复明确的默认值。
- 不按作者身份、星数、活跃度、许可证、是否 fork、是否归档、AI 判断或维护者好恶主动剔除条目。上游 API 的默认过滤和搜索上限也不能被静默包装成完整列表。
- 来源清单由订阅者选择。集市只显示条目及来源，不给清单背书，不附加集市自己的审核名单或隐藏规则。
- 缺字段、条目解析失败、来源不可达都如实显示，不编造评分或默默丢弃原始地址。归档、安装契约缺失等技术事实可展示；不能借此隐藏目录项。
- 审批授权的是一次 fork、安装或脚本执行，不是判定某个插件有无资格存在。保留宿主鉴权、沙箱与审批栈；没有操作授权就不执行，但目录展示不受其影响。
- 没有申请收录入口、审核后台、安全徽章、维护者推荐分、隐式推荐算法或自动安装更新。

## 已核实的缺口

1. host 固定按 stars 从 GitHub 取最多 100 条，再对这一页按 pushedAt 重排；client 没有分页。因此当前的最近更新不是全体命中结果的最新顺序，total 也不等于可浏览数量。
2. 切换排序仍发请求给 host，只是在缓存命中时不访问 GitHub；不能称为完全由 client 即时重排。
3. 列表缓存只在进程内，没有持久快照、容量淘汰、完整性信息或来源配置版本。刷新请求和普通请求可能互相覆盖。
4. 订阅只在页脚显示最多六个裸地址。writeSubscriptions 没有挂路由，界面无法管理订阅；来源错误没有在界面显示。
5. 订阅解析仅接受 GitHub 仓库，静默忽略其它地址，并丢弃 ref。安装端点同样只接收 repo，不能完整表达官方支持的 registry/path/tarball/git spec。
6. ghIdentity 把找不到可执行文件、未登录、权限问题、网络问题均归为 null；capabilities 将 null 统一投影为 gh:false。client 的四态不能弥补 host 信息不足。
7. performInstall 正常返回就标为 done，把 result.error 藏在 result 内；client 仅检查顶层 error，也未区分待构建授权、待重启、应用失败等终态。
8. 安装日志仅在 active 存在时展示，完成即消失；刷新或离开面板后不能恢复任务与日志；所谓已安装只是本次组件内存，没有从官方包管理器同步。
9. 轮询不核对 requestId，失败静默重试；其他卡片仍可提交，提交失败还可能先清掉当前进度。日志重传尾部，每 500ms 轮询可能产生重叠请求。
10. fork 目标由 login 和仓库名拼接，未依据实际返回仓库核验既有 fork、同名冲突与源仓库关联。提交锁定默认取 HEAD，没有保留指定版本意图。
11. 当前 GUI 路由同源检查后直接执行 fork/install，并未体现接入审批栈。不能把同源检查或点击安装视为已经接入审批。
12. 工具栏无响应式换行约束；卡片使用 12px 圆角；工具按钮是文字，缺乏完整键盘焦点、读屏状态与触屏禁用原因反馈。

## 第一阶段：正确性与操作授权

### 发现与排序

- 明确每次查询的来源、有效条件、排序范围、已加载数量与完整性。
- GitHub 大结果集使用服务端正确排序与分页，并按查询/排序/页分别缓存。仅完整取得的有限目录允许共享快照后本地全局排序。不能用热门一页伪装全局最近更新。
- 默认 topic 查询显式处理 fork 等上游默认行为。目录允许归档与低星条目；过滤仅按可见的使用者设置执行。
- 分开统计上游报告数量、已取得数量、去重后的显示数量；遇到上游检索上限或 incomplete_results 显式报告，不声称全量。

### 安装终态与任务身份

- 依据官方实际返回契约区分安装失败、等待构建授权、应用失败、等待重启、成功与取消，不靠 Promise 正常返回判成功。
- 任务按 requestId 查询和归属，避免旧响应覆盖新任务。提交期间及已有包操作期间禁止重复发起；先给明确忙碌状态，后续可添加显式队列。
- 活跃任务独立于列表卡片，搜索、切视图和关闭面板不能使任务消失。完成保留日志和结果，支持复制、下载、重试与官方可用的取消入口。
- 重新打开或刷新时读取 host 任务状态，并从官方包管理器同步安装/启用状态；host 重启后的未完成任务显示中断，不自动重做变更。
- 轮询不重叠，有断线状态与恢复入口；优先复用宿主已有事件传输，不另造长连接体系。

### gh 与 fork

- host 分别报告未找到 CLI、未登录、网络不可达、权限失败和可用账号，并允许重新检测；路径可配置，避免找到一次或找不到一次就永久缓存。
- 未找到 gh：Fork 安装灰色，hover 与键盘焦点提示“需要 CLI 工具支持”。触屏提供相同原因。网络失败不显示成未安装。
- 使用实际 fork 信息确认目标、上游关联、既有 fork 与同名冲突；遵循选择的 ref 并锁定实际安装提交，不默默切换到别的仓库或最新版。

### 审批接入

- 实施前查询 desktop 当前运行时的真实审批与包管理契约；如要读官方源码，先检查官方仓库更新再读。
- GUI 的操作意图必须走宿主支持的授权入口。若当前审批只接受 open turn 内的 agent/session，则设计关联会话工具的正式桥接，让真正的工具执行发起审批，GUI 只追踪同一任务。
- 桥接能力未核实前不承诺已可一键完成；不伪造 agent、turn 或批准结果，不另造弱确认来替代审批栈，也不在授权不可用时绕过执行。
- 授权内容只展示实际将做的操作、目标账号/profile/spec，以及官方报告的构建脚本需求。拒绝或取消不影响插件的列表可见性。

第一阶段交付：可信的结果与任务状态、正确排序与分页、准确 gh 状态、经过真实操作授权的安装流程。

## 第二阶段：把意图变成可操作配置

- 主区内使用“发现 / 订阅 / 已安装”视图，设置来源、过滤和排序；保存查询、滚动位置及安装方式。继续使用集市主区，不改成模态框或右侧栏主体。
- 来源管理支持增删、启停、刷新、导入导出以及每个来源的独立失败反馈。一个来源失败保留其它来源及上次成功快照，显示快照时间，不冒充实时结果。
- 订阅条目成为完整可操作的列表项；无 GitHub topic 的显式订阅也正常显示与安装。
- 保持兼容纯文本清单和注释，允许一行一个官方安装 spec。以可选明确格式补充名称/链接，不强迫作者填写审核材料。
- 内部统一最小条目结构：安装 spec（保留版本）、展示链接、已有元数据、来源集合。去重不丢来源，也不把不同版本无声合并。
- 提供统一“从地址安装”，覆盖官方 registry、绝对本地 path、tarball、git。有效 spec 原样委托包管理器解析和安装，不复制 pnpm 或官方解析器，不手写更窄的准入规则。
- GitHub 仓库提供直接安装与 Fork 安装；其它来源提供其真实支持的操作，不假装任意包来源均能 gh fork。
- 本人的默认安装方式可设为 fork，但这只是个人偏好；不把个人约束强加给其他使用者，不在 fork 失败时偷换成直接安装。

第二阶段交付：没有 topic 也能通过显式意图进入列表，四类官方安装来源均可用，所有主动过滤都能看到并清除。

## 第三阶段：体验与恢复能力

- 紧凑响应式工具栏：搜索输入、明确的排序菜单、来源与过滤入口、刷新图标、从地址安装。活动条件与缓存时间作为状态展示，不堆叠功能说明文字。
- 来源/作者已有头像作为小尺寸识别素材；卡片展示名称、描述、来源、星数/推送日期、真实安装状态，GitHub 或项目链接可直接打开。圆角不超过 8px，使用宿主主题与现有图标库，工具图标有 tooltip。
- 长名称和 spec 正常换行，窄窗口操作区移至下一行；不挤出视口、不使按钮动态改字时导致布局跳动。
- 首次加载 skeleton；刷新保留旧列表与滚动位置；失败标明来源和原因并能重试。取消过时请求，用请求序号阻止旧响应覆盖最新选择。
- 详情为主区内的条目详情视图，可返回原查询和位置；呈现来源已有 README、主页和版本信息，按需加载，不加入 AI 质量结论。
- 日志默认跟随新输出；查看旧日志时暂停跟随，提供回到底部、复制和下载。安装结束后日志仍在任务详情中。
- profile 内持久化必要快照与偏好；查询缓存有容量与过期管理、同请求合并、正确失效和手动刷新。快照有来源和时间，认证数据按 profile/账号隔离，不保存凭据。
- 支持键盘全流程、清晰焦点、读屏状态及触屏操作；亮暗主题均验证。

第三阶段交付：快速重开、状态连续、输入与刷新无竞态、桌面及窄窗口可操作。

## 验收标准

1. 显式订阅一个无 dsh-plugin topic 的地址后正常显示与可安装；低星、归档、fork 不因集市自己的判断消失。
2. 每个主动过滤都可以找到对应设置，清除后恢复；来源与去重依据可追溯，不同版本 spec 保留。
3. 用超过一页的构造数据检查全局排序、分页和完整性；最新但低星的条目不能因只读取热门一页被遗漏。
4. 温缓存重开目标为 300ms 内呈现旧快照；完整本地快照切换排序目标为 100ms 内完成且不访问网络。数据不完整时明确使用服务端排序，不伪称即时全局重排。
5. 切查询、排序、强制刷新并制造乱序响应，最新选择始终获胜。刷新失败不清空可读的旧结果。
6. 分别验证 gh 缺失、未登录、网络错误和正常账号；只有缺失显示“需要 CLI 工具支持”。
7. 覆盖四类官方 spec 与保留 ref；检查既有 fork、仓库同名冲突、请求取消及重试，不能换来源或版本来冒充成功。
8. 审批接受、拒绝、取消、不可用都可观察；拒绝和不可用时没有 fork/install 变更，但条目仍可见。构建脚本不自动授权。
9. 搜索、关闭面板、刷新页面后任务仍可找到，完成日志保留；失败/待授权/待重启均不能显示成已启用。
10. 用真实 Cordis 服务与官方安装契约验证接入；纯排序、spec 保留、缓存键和请求序号用纯函数测试，不维护一套假的宿主服务。
11. 在已鉴权的现有 GUI 和 desktop profile 验证实际加载版本，覆盖 1440px、768px、390px 及亮暗主题。没有溢出、遮挡或不可访问的禁用原因。

## 实施约束

按第一、第二、第三阶段推进。源码只按实际职责拆为少量来源/任务/UI 模块，保持 host 直接运行 JS，客户端提交预构建产物；不照搬旧市场的框架，不新增审核服务，不自造包管理器，不修改 DSH 本体。每阶段单独验证和记录；这份文档是方案，不是实现完成声明。
